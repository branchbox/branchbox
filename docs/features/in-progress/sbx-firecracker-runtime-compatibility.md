# SBX and Firecracker Runtime Compatibility

This checklist captures execution-boundary behavior proven or exposed by the Agentify coding-demo run on 2026-08-30. BranchBox must provide the same developer-environment facade whether the outer boundary is Docker Sandboxes locally or a Hetzner Firecracker microVM in Agentify's execution plane.

## Compatibility checklist

- [x] **Devcontainer config discovery (SBX):** generate the runtime-only config as `.devcontainer/.devcontainer.json`, a basename recognized by the current Dev Containers CLI, and pass it explicitly to `devcontainer up`, `exec`, and readiness probes.
- [x] **Devcontainer config discovery (Agentify in-guest):** the `in-guest` provider accepts an absolute supervisor manifest path, generates the same explicit `.devcontainer/.devcontainer.json` facade before host-side repository lifecycle processing, inspects the merged Dev Containers configuration, and uses the explicit path for start/probe/exec. Top-level `.devcontainer.json` remains fail-closed because an overlay cannot be generated without replacing source.
- [x] **Git metadata facade (SBX):** when the primary Compose service binds `/workspaces/main/.git`, append an ignored Compose override that binds the actual BranchBox `repo_root/.git`. Translate a lifecycle hook's `/workspaces/main/.git/worktrees/<name>` pointer back to the canonical repository worktree metadata, validate it, and write a relative host-portable pointer.
- [x] **Git metadata facade (Agentify in-guest):** the generated Compose override projects the canonical repository metadata without assuming the repo basename, while hook-disabled checkout and filter-driver rejection prevent repository code from running in the trusted guest. Pointer repair still runs after container lifecycle hooks.
- [x] **Suspend and restart semantics (SBX):** give the primary Compose service `restart: unless-stopped`. Port proxies resolve the stable container name on the Compose network instead of capturing an ephemeral container IP.
- [x] **Restart semantics (Agentify in-guest):** every start/exec reconciles the devcontainer from the explicit config, inspects the current container boundary, and rebuilds stable-name loopback proxies. Agentify still owns microVM resume/reboot and must re-invoke reconciliation from the signed assignment.
- [x] **Host-file projection (SBX):** copy only configured `${localEnv:HOME}/.ssh/*.pub` bind sources that are regular, non-symlink files into the sandbox home before Dev Containers starts. Remove only an exact empty public-key path left by a failed bind, and set mode `0644`. Private keys and arbitrary home-directory files are never copied by this facade.
- [x] **Mount and identity projection (Agentify in-guest):** ignore repository-declared service volumes and synthesize only the canonical task worktree at a normalized effective folder below platform-owned `/workspaces` plus the canonical repository Git metadata mapping. Accept only owner-only regular-file paths plus SHA-256 digests below the manifest sibling `materializations/` directory and mount non-environment files read-only below `/run/branchbox/leases`. Exactly one canonical typed `project-environment` materialization may instead be attached to the primary Compose service as a required raw env file; values never enter the facade or runtime evidence. Ambient homes, relative credential files, shared auth volumes, supervisor directories, host env files, outside/in/from-Docker feature aliases, local Docker/containerd/Podman/BuildKit sockets, and remote daemon endpoints are removed or rejected before start and verified absent from the running container.
- [x] **Exclusive port publication (Agentify in-guest):** clear devcontainer `appPort`/`forwardPorts` policy plus repository `ports` and `expose` declarations on every Compose service, start only the primary service plus its validated Compose dependency closure, and publish only signed assignment ports through BranchBox-owned loopback proxies targeting the inspected primary container. Repository SSH bindings such as `127.0.0.1:2222:22` cannot survive the generated facade, and a dependency cannot hijack a signed app port by declaring the same exposed port. Multi-service routes require a future signed service identity.
- [x] **Partial-start cleanup (Agentify in-guest):** pre-record workspace/Compose/proxy identity before `devcontainer up`, recover projects from exact Dev Containers and Compose ownership labels when startup fails, remove dependency-only containers/networks/volumes plus lease files, and delete the failed task worktree/branch. No-registry recovery uses owner-only provider state and never falls back to repository modules or adapters.
- [x] **Coding-session shared memory (Agentify in-guest):** replace repository `--shm-size` requests with a private, bounded 1 GiB `/dev/shm` on the primary service. Host IPC remains forbidden; the Firecracker outer boundary must budget this allocation within the VM memory limit.
- [x] **Coding-agent identity lease transport (Agentify in-guest):** BranchBox accepts opaque typed lease/materialization paths and reports only non-secret lease records. The fixed Codex lane inherits only the name `OPENAI_API_KEY` into a single `docker exec`; ordinary exec scrubs it and post-start inspection rejects persistence. Agentify remains responsible for authorization, lease issuance/expiry, and erasing the outer sealed bundle.
- [x] **Exact-head guest-base publication:** the Firecracker lifecycle workflow checks out the pull-request head rather than GitHub's synthetic merge commit, proves the full local-VM lifecycle and zero host residue, and only then publishes `vmlinux`, `kernel.config`, the Docker-export rootfs archive, and a strict manifest. Immediately before upload, it verifies the kernel, kernel-config, and rootfs-archive digests, archive size, complete fixed kernel requirement list, source repository, and exact source commit. Downstream consumers must independently authorize and verify the artifact before installing their managed runtime boundary; the local-VM SSH and sudo identity is not part of that contract.
- [x] **Portable guest kernel policy capability:** the guest-base manifest and local validator independently require a versioned legacy IPv4 xtables kernel contract covering chains, conntrack, UID-owner matching, TCP-reset rejection, bridge filtering, and NAT/MASQUERADE. A trusted disposable network-namespace probe attaches a consumer-neutral user chain to `OUTPUT`, exercises an exact destination/port UID-owner rule there, and verifies conntrack separately without giving the coding devcontainer `NET_ADMIN`; provider, domain, chain, and integration policy remain consumer-owned.
- [ ] **Browser evidence sibling (Agentify outer):** launch a supervisor-owned browser helper in the same Firecracker guest so it can consume only the signed BranchBox loopback application URL and write screenshots/video to an assignment-scoped evidence directory. The helper must receive no Docker socket/API endpoint, repository bind, project secret materialization, or authority to select another Compose service. BranchBox supplies the primary-container proxy; Agentify owns browser sandboxing, lifecycle, and proof collection.
- [ ] **DNS SRV and tunnel egress (both):** prove SRV lookup for `_v2-origintunneld._tcp.argotunnel.com`, TCP egress to the selected Cloudflare edge on port `7844`, connector registration, and an HTTP request through the assigned hostname.

## Cloudflared boundary decision

The nested Docker connector is not yet portable through Docker Sandboxes' transparent TCP proxy. A DoH relay inside the sandbox restores the Cloudflare SRV records, and direct hostname tests to `region1.v2.argotunnel.com:7844` and `region2.v2.argotunnel.com:7844` work. However, cloudflared's HTTP/2 TLS SNI is `h2.cftunnel.com`. The SBX proxy attempts to dial that certificate-only name, which has no A/AAAA record, instead of preserving cloudflared's already-selected edge IP. The connector then fails before registration.

For the current demo only, cloudflared therefore runs on the macOS outer boundary and targets the SBX-published loopback port. This is a recorded workaround, not the target topology: the connector token remains in the ignored BranchBox secure directory, the application devcontainer never receives the platform Cloudflare authority, and teardown must remove the connector plus route.

BranchBox and the Agentify execution plane must choose and test one of these models:

1. Run cloudflared at the outer SBX/Firecracker boundary and route it to the devcontainer's stable published service address.
2. Keep cloudflared inside the devcontainer network, but ensure the microVM egress path preserves the original destination IP while using SNI only for TLS policy.

The Firecracker implementation must not inherit the SBX failure mode. Its acceptance test is the full chain: SRV answer → edge TCP/TLS on `7844` → active connector → public hostname → current devcontainer service → browser-visible response.

## Runtime-only files

BranchBox owns and ignores these generated files; linked application source remains unchanged:

- `.devcontainer/.devcontainer.json`
- `.devcontainer/.branchbox-sbx-compose.yaml`

The same filenames are used by `in-guest`; its provider-private cleanup record is `.branchbox/runtime/in-guest/<run-id>.json`. See [Agentify In-Guest Devcontainer Provider](in-guest-devcontainer-provider.md) for the signed handoff, sanitizer, and deterministic residue contract.

They are regenerated on each SBX feature start. If the source devcontainer no longer needs an SBX Compose facade and no `runServices` override is configured, BranchBox removes both stale generated files without editing the source `devcontainer.json` or Compose files. Feature teardown removes them with the BranchBox worktree.
